# 结构化提示词设计

当提示词变得复杂时，纯自然语言会产生歧义。结构化提示词使用标签或分隔符划分语义区域，让模型清晰地理解每部分内容的用途。

## XML 标签范式

使用 XML 风格的标签是目前业界最主流的结构化方案：

```text
<system>
你是一个资深的 DevOps 架构师。你的任务是分析系统日志并定位故障根因。
请严格遵循以下规则：
1. 仅基于提供的日志内容进行推断，不得臆造信息。
2. 如果无法确定根因，请明确输出 "INSUFFICIENT_DATA"。
</system>

<context>
[此处动态注入系统日志切片]
</context>

<task>
请分析上述日志，按以下 JSON 格式输出结论：
{"root_cause": "...", "confidence": 0.0-1.0, "suggested_fix": "..."}
</task>
```

这种范式的优势：

- `<system>` 设定角色与全局约束
- `<context>` 注入动态上下文，与指令明确隔离，可防御提示词注入
- `<task>` 规范输出格式，便于工程解析

## Few-shot 示例

给模型展示"输入 → 期望输出"的样例，是提升输出稳定性最有效的手段之一：

```text
请将用户反馈分类为 bug / feature / question 之一。

示例：
输入：登录按钮点了没反应
输出：{"category": "bug"}

输入：希望支持深色模式
输出：{"category": "feature"}

现在请分类：
输入：请问怎么导出数据？
输出：
```

## 思维链（Chain-of-Thought）

对于需要推理的任务，要求模型"先思考再回答"能显著提升准确率：

```text
请一步步分析这个问题，先列出你的推理过程，
最后在 <answer> 标签中给出最终答案。
```

思维链的本质是让模型把中间推理步骤显式生成为 Token，为后续的结论提供更充分的条件概率支撑。

## 提示词版本管理

在生产环境中，**Prompt 就是业务逻辑**，必须像代码一样管理：

1. **外置化**：用 YAML/JSON 文件或数据库存储提示词模板，不要硬编码在业务代码中
2. **绑定模型版本**：记录提示词验证通过的模型版本，模型升级后需要回归测试
3. **支持 A/B 测试与回滚**：线上可动态切换版本，出现质量下降能秒级回滚

> **工程提示**：使用模板引擎（如 Mustache）管理提示词中的变量插值，实现提示词结构与数据的解耦。
